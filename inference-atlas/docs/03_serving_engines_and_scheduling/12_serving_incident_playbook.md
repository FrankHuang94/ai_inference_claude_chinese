## 0. 使用说明

**进入条件**：SLO 告警触发，或用户反馈异常。

**处置原则**：

1. **先止血，再定位**。恢复服务优先于查明根因；
2. **一次只改一个变量**，否则无法归因；
3. **每步记录时间与观测值**，用于事后复盘；
4. **降级优于崩溃**：宁可主动降低服务等级，不可等待雪崩。

## 2. P99 飙升，均值正常

**最可能的三个原因**（按概率排序）：

| # | 原因 | 判定信号 | 立即动作 |
|---:|---|---|---|
| 1 | KV 压力触发抢占重算 | **抢占率 > 0**，KV 利用率接近上限 | 收紧准入阈值；下调最大批 |
| 2 | 长 prompt 阻塞 decode | ITL 出现**离散尖峰**，与新请求到达相关 | 启用/收紧 chunked prefill |
| 3 | 批内长短请求干扰 | ITL **均匀抬升**，批内长度方差大 | 启用长度感知组批或分池 |

**判别关键**：看 ITL 分布形状。

| 形状 | 指向 |
|---|---|
| 离散尖峰 | 原因 2（prefill 阻塞） |
| 均匀抬升 | 原因 3（批内干扰） |
| 少数极端值 | 原因 1（抢占重算） |

**若三者均不符**：检查温度与频率曲线（热降频，见 [§8](#8-单实例异常)）、以及网络侧（跨节点部署时的集合通信抖动）。

## 3. TTFT 高，TPOT 正常

**排查顺序**：

| 步骤 | 检查 | 若异常 |
|---:|---|---|
| 1 | **队列深度与排队时延** | 排队积压 → 见 [§5](#5-吞吐骤降) 与 [§7](#7-过载后不恢复) |
| 2 | 输入长度分布是否变化 | 长请求增多 → chunked prefill、按长度分池 |
| 3 | **前缀缓存命中率** | 命中率骤降 → 检查缓存感知路由、prompt 是否引入变化内容（如时间戳） |
| 4 | Prefill token 预算占比 | 被 decode 挤占 → 下调 `max_decode_share` 或调大 `T_budget` |
| 5 | Tokenizer 耗时 | CPU 瓶颈 → 扩容 CPU 或前移分词 |
| 6 | 冷启动事件 | 扩容中 → 见 [§10](#10-降级手册) |

**最常见的两个**：步骤 1（排队）与步骤 3（缓存命中率骤降）。后者常由一次 prompt 模板变更引起——**发布关联性检查是首要动作**。

---

## 4. TPOT 高，TTFT 正常

| 步骤 | 检查 | 若异常 |
|---:|---|---|
| 1 | **显存带宽利用率** | 已饱和 → 属正常上限，需扩容或量化 |
| 2 | 有效批大小 | 偏小 → 检查准入是否过严、流量是否不足 |
| 3 | 上下文长度分布 | 变长 → 进入 KV 主导区，考虑 KV 量化 |
| 4 | 量化配置是否变更 | 回退到高精度 → 确认发布 |
| 5 | **温度与频率** | 降频 → 见 [§8](#8-单实例异常) |
| 6 | 集合通信耗时（分布式） | 上升 → 检查网络、拓扑映射 |
| 7 | 采样/约束解码开销 | 新启用约束解码 → 评估其成本 |

## 5. 吞吐骤降

| 判定 | 信号 | 动作 |
|---|---|---|
| **Cache thrashing** | 抢占率高、KV 利用率满、吞吐低于更小批时 | **立即下调最大批与准入阈值** |
| 实例掉线 | 实例数减少 | 检查节点健康、触发扩容 |
| 热点 | 单实例负载远高于其他 | 检查路由评分、缓存亲和权重 |
| 降频 | 频率曲线下降 | 见 [§8](#8-单实例异常) |
| 上游变化 | 输入长度或并发模式突变 | 与业务方确认 |

**Cache thrashing 是最危险的**，因为它有正反馈：抢占 → 重算 → 方差增大 → 排队加剧 → 更多抢占。**必须从入口切断**（收紧准入），仅调批大小可能不足。

## 6. 错误率上升或大量 429

| 类型 | 判定 | 动作 |
|---|---|---|
| 准入控制拒绝 | 429 且拒绝原因为容量 | 属预期保护；评估是否扩容 |
| **重试风暴** | 429 后总请求量不降反升 | **启用背压 + Retry-After**；与客户端方协调退避 |
| 配额超限 | 429 集中在特定租户 | 确认是否为攻击或配置错误 |
| 上游超时 | 5xx 伴随连接错误 | 检查网关与后端连通性 |
| OOM | 实例崩溃重启 | 下调批大小；检查 $M_{rt}$ 标定 |

**重试风暴的识别**：拒绝率上升的同时**总到达率也上升**。这是一个正反馈，必须靠背压与客户端退避打破，单纯拒绝会加剧。

## 7. 过载后不恢复

**这是最严重的状态**：外部流量已回落，系统仍积压。

**机制**（见 [模块 01 第 3 章](../01_foundations_and_metrics/03_queueing_theory_for_inference.md)）：

```text
积压 → KV 压力 → 抢占 → 重算 → 有效服务能力下降 + 方差增大 → 积压加剧
```

**处置顺序**（严格按序）：

| # | 动作 | 目的 |
|---:|---|---|
| 1 | **大幅收紧准入阈值**（临时） | 从入口切断输入 |
| 2 | 下调最大批大小 | 降低 KV 压力 |
| 3 | 暂停抢占（若可配置） | 打破重算循环 |
| 4 | 观察抢占率是否归零 | 确认循环已断 |
| 5 | 等待积压消化 | 队列深度下降 |
| 6 | **逐步**放松准入 | 一次只放松一档 |
| 7 | 恢复原配置 | 确认稳定后 |

**关键**：第 1 步必须够狠。温和收紧可能不足以打破正反馈，反而延长故障时间。

**事后必做**：复盘为什么准入控制没有在过载前生效——通常是阈值设置过松或缺少某个判据维度。

## 8. 单实例异常

| 症状 | 判定 | 动作 |
|---|---|---|
| **热降频** | 温度高，频率随时间下降 | 检查散热；临时降低该实例权重 |
| **功率封顶** | 功率贴住上限，高负载时立即出现 | 检查机架功率预算 |
| 显存泄漏 | 显存占用只增不减 | 重启实例；排查引擎版本 |
| 硬件故障 | ECC 错误、XID 错误 | 摘除节点，报修 |
| 版本不一致 | 该实例行为与其他不同 | 确认发布是否完整 |

**热降频与功率封顶的区分**：前者**运行一段时间后**逐渐出现，后者**高负载时立即**出现。

## 9. 区域级故障

| 步骤 | 动作 |
|---:|---|
| 1 | 确认故障范围（单可用区 / 整区域 / 依赖服务） |
| 2 | **切换流量到备用区域**（若已部署） |
| 3 | 若无备用区域：启用降级模式（见 [§10](#10-降级手册)） |
| 4 | 通知用户（状态页） |
| 5 | 评估备用区域容量是否足够；不足则同时限流 |
| 6 | 故障恢复后**逐步**回切，避免瞬时全量冲击 |

**关键提醒**：备用区域的容量通常小于主区域。**切换后必须同时收紧准入**，否则会把故障从一个区域扩散到两个。

## 10. 降级手册

**降级顺序**（从代价最小到最大）：

| # | 降级动作 | 影响 | 恢复难度 |
|---:|---|---|---|
| 1 | 下调 reasoning 的思考预算 | 复杂任务质量 | 低 |
| 2 | 收紧准入，优先保高 tier | 低 tier 可用性 | 低 |
| 3 | 限制最大上下文长度 | 长文档功能 | 低 |
| 4 | 关闭非必要的约束解码/后处理 | 输出格式保障 | 低 |
| 5 | 路由到更小模型档位 | 全局质量 | 中 |
| 6 | 限制最大输出长度 | 长回复被截断 | 中 |
| 7 | 关闭流式，改批量返回 | 体验 | 中 |
| 8 | 拒绝低 tier 全部请求 | 可用性 | 低 |

**原则**：**优先降低"每请求的资源消耗"，其次才降低"服务的请求数"**。前四项都属前者，对用户可见度低。

**必须事先准备的**：每一项降级都应当是**一个配置开关**，而非需要发版的代码修改。在事故中改代码是不可接受的。

## 11. 事故记录模板

```markdown
## 事故 <ID>：<一句话描述>

- 开始时间 / 发现时间 / 恢复时间：
- 影响范围：受影响租户、请求比例、SLO 违约时长
- 触发信号：哪个告警、观测值

### 时间线
| 时间 | 观测 | 动作 | 结果 |
|---|---|---|---|

### 根因
（区分**触发因素**与**根本原因**。流量上涨是触发因素，缺少准入控制才是根本原因。）

### 为什么没有更早发现
（监控缺口分析）

### 为什么影响这么大
（防护缺口分析：哪一层的保护没有生效）

### 改进项
| # | 改进 | 类型（监控/防护/容量/流程） | 负责人 | 期限 |
|---:|---|---|---|---|
```

**复盘纪律**：**区分触发因素与根本原因**。"流量突增"几乎从不是根本原因——根本原因是"系统在流量突增时没有正确降级"。只记录触发因素的复盘不会带来改进。

## 12. 预防清单

在事故发生前应当已经就位的：

- [ ] 准入控制已实现，且覆盖显存侧与时延侧两个判据
- [ ] 三个关键指标有告警：排队时延、KV 利用率、抢占率
- [ ] 所有降级动作都是配置开关，无需发版
- [ ] 已做过**过载回落演练**（正常压测不覆盖此场景）
- [ ] 已做过区域切换演练
- [ ] 客户端有退避重试策略，服务端返回 Retry-After
- [ ] 各实例的温度与频率纳入监控
- [ ] 有状态页与用户通知流程
- [ ] 值班人员知道本手册的位置

**第 4 项最常缺失**：正常负载下的压测无法暴露"过载后不可恢复"的问题，必须专门演练。
