## 本章导读

推理 benchmark 是这个领域里最容易产生错误结论的载体。原因不是造假，而是**配置空间太大**：模型、量化、序列长度、并发、软件版本、cache 状态、指标定义——任意一维的差异都能让同一硬件的数字相差数倍。当两份 benchmark 只报告"吞吐 X tokens/s"而不报告这七个维度时，比较它们在数学上没有意义。

本章给出一份**可操作的审读清单**：拿到任何一份 benchmark，先按清单核对，凡缺项即判定为"不可跨来源比较"。这个判断本身就是有价值的结论——它把"我不知道该信谁"转化为"这份材料不足以支持该结论"。

本章不教你如何做 benchmark（那是 [模块 11](../11_benchmarking_reliability_and_observability/) 的内容），只教你如何**不被 benchmark 误导**。

## 学习目标

读完本章后，读者应能够：

1. 对任意一份推理 benchmark 快速判定其是否可比、可复现、可采信；
2. 识别六类最常见的失真手法，并说明每一类如何被制造出来；
3. 解释为什么"吞吐"和"时延"必须一起报告，单独报告任一项都可能误导；
4. 说明 MLPerf Inference 能回答与不能回答的问题。

## 核心结论

- **配置缺失即不可比**。缺少模型版本、软件版本、序列长度、并发、指标定义中任一项，该数字都不能与其他来源并列。
- **单独的吞吐数字几乎无意义**。吞吐总可以通过增大 batch 提升，代价是时延；不给出时延约束的吞吐是自由参数。
- **理论峰值算力不能预测推理性能**。LLM decode 是 memory-bound，峰值 FLOPS 与实际 tokens/s 之间没有稳定映射。
- **厂商 benchmark 不必然造假，但必然是选择性的**。它展示的是该产品表现最好的配置点，这是合理的商业行为，也是你必须校正的偏差。

## 1. 问题定义、系统边界与工作负载

### 1.1 一份 benchmark 到底在测什么

任何推理 benchmark 都是在一个高维配置空间中取的一个点：

$$
\text{性能} = f(\underbrace{\text{模型}, \text{量化}}_{\text{模型维}}, \underbrace{\text{硬件}, \text{数量}, \text{网络}}_{\text{硬件维}}, \underbrace{\text{引擎}, \text{版本}, \text{参数}}_{\text{软件维}}, \underbrace{S_{in}, S_{out}, \text{并发}, \text{cache 状态}}_{\text{负载维}})
$$

**关键认识**：这个函数在多数维度上都不是单调的，也不可外推。在 $S_{in}=128, S_{out}=128$ 下测得的吞吐，无法推出 $S_{in}=8192$ 下的表现——后者的 prefill 成本和 KV 显存占用完全不同，可能已经落入另一个瓶颈区间。

因此，**跨配置的比较需要配置对齐，而不是数字换算**。

### 1.2 benchmark 的三种类型

| 类型 | 目的 | 可信度基础 | 主要局限 |
|---|---|---|---|
| 标准化基准（如 MLPerf Inference） | 跨厂商可比 | 规则统一、结果需提交审核 | workload 固定，未必贴近你的生产负载 |
| 厂商官方 benchmark | 展示产品能力 | 有完整硬件与软件控制权 | **选择性配置**，通常取最有利点 |
| 第三方 / 社区 benchmark | 独立视角 | 无厂商利益 | 调优水平参差，可能低估某方 |

三类都有价值，前提是**不把它们混在一张排名表里**。本库通过 `benchmarks.csv` 的 `source_type` 字段强制区分。

## 2. 原理、数学与性能模型

### 2.1 为什么吞吐与时延必须一起报告

考虑一个简化模型：系统以批大小 $B$ 运行，每次迭代耗时 $T_{iter}(B)$，则吞吐为

$$
\text{Throughput} \approx \frac{B}{T_{iter}(B)}
$$

由于 decode 是 memory-bound，权重读取时间在小 batch 下几乎与 $B$ 无关，因此 $T_{iter}(B)$ 在一定范围内增长缓慢，吞吐近似随 $B$ 线性上升。

而单个请求感受到的每 token 时延就是 $T_{iter}(B)$，它随 $B$ **单调不减**。

**结论**：吞吐与 TPOT 由同一个旋钮（batch 大小）反向控制。只报告吞吐等于隐藏了这个旋钮的位置。

**正确的报告方式**是给出**时延约束下的吞吐**，即 goodput：

$$
\text{Goodput} = \text{满足 SLO 的请求所贡献的吞吐}
$$

报告 goodput 必须同时给出所用的 SLO 定义，否则同样不可比。

**局限**：上式忽略了 KV 显存对 $B$ 的上限约束、以及批内序列长度不齐带来的效率损失，属于教学近似。

### 2.2 为什么峰值算力预测不了推理性能

Roofline 模型给出可达性能上界：

$$
\text{Attainable} = \min(\text{Peak Compute},\; \text{Arithmetic Intensity} \times \text{Memory Bandwidth})
$$

其中算术强度 = 计算量 / 内存访问量（FLOP/byte）。

LLM decode 阶段每步只处理 1 个 token 却要读取全部权重，算术强度极低，因此 $\text{Attainable}$ 由右项（带宽）支配。这意味着：

- 两块峰值算力相同但带宽差 2 倍的卡，decode 吞吐可能差近 2 倍；
- 反过来，宣传 "X PFLOPS" 的卡在 decode 上未必优于算力更低但带宽更高的卡。

**这是本库反复强调"必须区分理论峰值与实测"的物理原因**，不是措辞洁癖。

## 3. 实现机制与系统设计

### 3.1 审读清单（最低充分条件）

拿到一份 benchmark，逐项核对。**任一项缺失 → 标记为不可跨来源比较。**

| # | 必须明确 | 缺失后果 |
|---:|---|---|
| 1 | 模型名称与**具体版本/checkpoint** | 同名模型不同版本性能可差数倍 |
| 2 | 模型参数化（dense/MoE、总参数、激活参数） | MoE 与 dense 的资源画像完全不同 |
| 3 | **量化方案**（含 KV cache 是否量化） | 量化可使吞吐翻倍，同时改变质量 |
| 4 | 硬件型号与**数量** | 单卡与八卡结果不可直接并列 |
| 5 | 网络配置（多节点时） | 通信可能是主导项 |
| 6 | **软件栈与版本号**（引擎、驱动、CUDA） | 引擎版本间性能差异常见 |
| 7 | **输入 token 长度**（或分布） | 决定 prefill 成本与 KV 占用 |
| 8 | **输出 token 长度**（或分布） | 决定 decode 段占比 |
| 9 | **batch 大小 / 并发数** | 吞吐-时延权衡点的位置 |
| 10 | warmup 方式 | 未 warmup 会混入编译与首次分配开销 |
| 11 | **cache 状态**（冷/热、前缀命中率） | 前缀命中可使 TTFT 相差一个量级 |
| 12 | tokenizer | 影响 token 计数口径 |
| 13 | 是否流式 | 影响 TTFT 的测量含义 |
| 14 | **时延指标的精确定义**（TTFT 是否含排队） | 最常见的口径分歧点 |
| 15 | **吞吐的精确定义**（output token 还是 total） | 可造成约 2 倍差异 |
| 16 | **分位数与样本量** | 只报均值会掩盖尾部问题 |
| 17 | 功耗测量边界（chip/node/rack/facility） | 跨边界比较无效 |
| 18 | 成本口径与利用率假设 | $/token 高度依赖假设 |
| 19 | 可复现配方是否公开 | 决定可复现性等级 |
| 20 | caveats | 没有 caveat 的 benchmark 本身就是 caveat |

本库的 [`benchmarks.csv`](../../data/benchmarks.csv) 把这 20 项固化为字段，由 [`scripts/benchmark_audit.py`](../../scripts/benchmark_audit.py) 强制校验。

### 3.2 六类常见失真

以下手法**大多不涉及造假**，而是通过合法的配置选择制造有利印象。识别它们是审读的核心技能。

| # | 手法 | 表现 | 如何识破 |
|---:|---|---|---|
| 1 | **最优点采样** | 只报告自家产品最擅长的序列长度/并发 | 要求提供扫描曲线而非单点 |
| 2 | **口径不对称** | 自家 TTFT 不含排队，对手含 | 核对指标定义是否同源 |
| 3 | **调优不对称** | 自家用专家调优，对手用默认配置 | 看是否公开双方配置文件 |
| 4 | **量化不对称** | 自家 INT4，对手 BF16，只比吞吐不比质量 | 核对精度与质量评测是否同时给出 |
| 5 | **峰值当实测** | 用理论 FLOPS 推算"可支持 X 用户" | 看是否有实际 tokens/s 测量 |
| 6 | **cache 状态不透明** | 前缀全命中下测 TTFT | 核对 cache 状态是否声明 |

**一个实用启发**：如果一份对比材料中，己方与对方的**软件版本发布日期相差超过半年**，基本可以判定调优不对称。

### 3.3 MLPerf Inference 的定位

MLPerf Inference 是目前跨厂商可比性最强的公开基准，其价值来自统一的规则、场景定义与结果审核流程。

**它能回答**：在**统一规则与统一 workload** 下，不同厂商提交的系统表现如何；厂商是否愿意公开接受同一套约束的检验。

**它不能回答**：

- 你的生产 workload 上的表现——MLPerf 的 workload 是固定的，序列长度分布与真实业务往往不同；
- 成本效率——除非结合价格与功耗数据，而这些通常不在结果内；
- 长期稳定性、多租户干扰、故障恢复——基准测的是稳态性能；
- open division 结果的横向可比性——open division 允许修改模型，因此结果之间不必然可比。

**因此**：把 MLPerf 当作"厂商是否具备工程能力的一个证据"是合理的；把它当作"该硬件在我的业务上会有多快"则是外推错误。详见 [模块 11](../11_benchmarking_reliability_and_observability/)。

## 4. 性能、成本、能耗与可靠性 trade-off

审读时要意识到 benchmark 通常只覆盖五维中的一到两维：

| 维度 | 常被报告 | 常被省略 | 省略的后果 |
|---|---|---|---|
| 时延 | TTFT、TPOT 均值 | 分位数、样本量 | 尾部问题不可见 |
| 吞吐 | tokens/s | goodput、SLO 定义 | 无法判断是否可用 |
| 成本 | 偶尔给 $/1M tokens | 利用率假设、是否含网络与运维 | 数字不可迁移 |
| 能耗 | 偶尔给 W | 测量边界、是否含散热 | 跨边界比较无效 |
| 可靠性 | 几乎不报告 | 全部 | 稳态性能 ≠ 生产可用性 |

**结论**：一份只报告吞吐的 benchmark，最多能支持"该系统在某配置下能达到该吞吐"这一条结论，不能支持任何选型判断。

## 5. benchmark、真实案例或公开部署案例

本节给出本库对已收录来源的处理方式作为示例。

**收录标准**：本库的 [`benchmarks.csv`](../../data/benchmarks.csv) 只收录第 3.1 节清单**基本完备**的结果。这导致收录数量远少于网络流传的对比图——这是刻意的取舍。

**处理不完备来源的方式**：不是丢弃，而是收录并在 `caveats` 中写明缺失项、在 `reproducibility_level` 中标注 `部分可复现` 或 `不可复现`。读者据此自行判断。

**对论文数字的处理**：本库引用论文的机制性结论（如"分页管理可回收 KV 显存浪费"），但**不脱离实验配置复述加速倍数**。原始数字与完整配置见 [模块 13](../13_research_papers_and_technical_reports/) 的论文卡片。

## 6. 设计决策框架

当你需要**基于 benchmark 做选型决策**时：

1. **先写下你的 workload**：输入/输出长度分布、并发、SLO。没有这一步，任何 benchmark 都无从匹配；
2. **筛掉配置不匹配的**：序列长度差一个量级的结果直接排除，不要试图换算；
3. **筛掉不可比的**：按 3.1 清单，缺项超过 3 项的降级为"参考"而非"依据"；
4. **区分来源类型**：厂商官方结果用于确认能力上界，第三方结果用于估计实际可达；
5. **补做关键点验证**：最终候选方案上，在你自己的 workload 上跑一次——这一步不可省略；
6. **把成本与功耗纳入**：$/1M tokens 与 J/token 往往改变排序；
7. **验证降级行为**：过载时的表现比稳态峰值更能决定生产可用性。

**决策纪律**：benchmark 用于**缩小候选集**，不用于**做出最终决定**。最终决定需要在自己的 workload 上验证。

## 7. 常见失败模式与排查路径

| 失败模式 | 表现 | 根因 | 纠正 |
|---|---|---|---|
| 外推序列长度 | 上线后 TTFT 远超预期 | 用短序列结果推长序列 | 按实际长度分布重测 |
| 忽略 cache 状态 | 生产 TTFT 高于测试 | 测试时前缀全命中 | 声明并区分冷/热态 |
| 只看均值 | P99 严重超标 | 未报告分位数 | 要求分位数与样本量 |
| 用峰值算力估容量 | 实际吞吐远低于估算 | decode 是 memory-bound | 用带宽而非算力估算 |
| 忽略量化的质量代价 | 吞吐达标但质量下滑 | 只比性能不比质量 | 性能与质量同时评估 |
| 单节点结果推多节点 | 分布式后 TPOT 恶化 | 未计入集合通信 | 在目标拓扑上实测 |
| 忽略软件版本 | 复现不出公开结果 | 引擎版本不同 | 锁定版本号 |

## 9. 小结

推理 benchmark 是高维配置空间中的采样点，跨配置比较需要配置对齐而非数字换算。审读的核心是一份 20 项的最低充分条件清单：缺项即判定不可比。六类常见失真大多通过合法的配置选择制造，识别它们依赖对配置维度的敏感。吞吐与时延由同一个旋钮反向控制，因此必须一起报告；峰值算力因 decode 的 memory-bound 特性而无法预测推理性能。benchmark 的正确用途是缩小候选集，最终决策必须在自己的 workload 上验证。
