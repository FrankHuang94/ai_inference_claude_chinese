## 本章导读

推理相关岗位的面试与传统 ML 岗位有一个结构性差异：**它考察的是系统能力而非模型能力**。面试官关心的不是你能不能训出好模型，而是你能否在显存、带宽、时延、成本的多重约束下做出可辩护的工程决策。

这带来一个具体后果：**能背出"vLLM 用了 PagedAttention"没有价值，能算出"这个配置下 KV cache 要占 X GB，因此并发上限是 Y"才有价值**。前者是检索，后者是推理。面试官区分二者的方式通常是追问一层——"那如果上下文翻倍呢"、"如果换成 GQA 呢"。

本章给出能力地图、准备策略与常见的准备误区。具体题目与完整参考答案在 [模块 17](../17_interview_prep/)。

## 学习目标

读完本章后，读者应能够：

1. 说出目标岗位对应的能力权重，并据此分配准备时间；
2. 识别自己准备中的"检索型知识"与"推导型知识"的比例失衡；
3. 用一套固定结构组织 2–5 分钟的口头回答；
4. 制定一份与自身起点匹配的准备计划。

## 核心结论

- **推理面试的核心考点是约束下的权衡**，不是技术名词的覆盖面。
- **必须能动笔算**：KV 显存、算术强度、排队时延、成本分解。这四类计算在面试中出现频率极高，且无法靠背诵通过。
- **回答必须有结构**：结论先行 → 原理 → 路径 → 权衡 → 案例 → 局限。无结构的回答即使内容正确也会被低估。
- **说"不知道"是有效策略**，前提是紧接着说出你会如何测量或验证。这恰恰是工程能力的体现。

## 1. 问题定义、系统边界与工作负载

### 1.1 岗位与能力权重

不同岗位的考察重心差异很大，用同一套准备应付所有岗位是低效的。

| 岗位 | 核心考察 | 次要考察 | 主要模块 |
|---|---|---|---|
| Inference Engineer | serving、调度、KV、性能排查 | kernel、量化 | [01](../01_foundations_and_metrics/)–[05](../05_decoding_and_generation_algorithms/) |
| ML Systems Engineer | 分布式、并行、系统设计 | 硬件、网络 | [03](../03_serving_engines_and_scheduling/)、[06](../06_distributed_and_moe_inference/) |
| AI Infrastructure Engineer | 集群、编排、容量、可靠性 | 网络、数据中心 | [09](../09_datacenter_power_thermal_and_operations/)、[11](../11_benchmarking_reliability_and_observability/)、[12](../12_open_source_deployment_and_reproduction/) |
| Compiler Engineer | IR、图优化、算子融合、autotuning | 硬件微架构 | [04](../04_compilers_runtimes_and_kernels/) |
| GPU Performance Engineer | kernel、profiling、roofline、占用率 | 量化 | [04](../04_compilers_runtimes_and_kernels/)、[01](../01_foundations_and_metrics/) |
| Serving Engineer | 批处理、QoS、autoscaling、事故处理 | 可观测性 | [03](../03_serving_engines_and_scheduling/)、[11](../11_benchmarking_reliability_and_observability/) |
| AI Hardware / ASIC | 微架构、内存层次、封装、互连 | workload 特征 | [07](../07_hardware_and_server_architecture/)、[08](../08_networking_and_interconnect/) |
| Datacenter Network | 拓扑、拥塞、RDMA、光互连 | 集合通信 | [08](../08_networking_and_interconnect/) |
| Edge AI | 端侧约束、量化、SoC、异构执行 | 小模型 | [10](../10_edge_and_on_device_inference/) |
| Technical Strategy | 技术路线、单位经济性、竞争格局 | 全栈概览 | [14](../14_company_and_ecosystem_landscape/)–[16](../16_research_frontiers/) |

**使用方法**：确定目标岗位后，把 70% 时间投入"核心考察"列对应的模块，20% 给"次要考察"，10% 给全栈概览（[模块 00](README.md)）。跨岗位平均用力是准备阶段最常见的浪费。

### 1.2 题型分布

推理面试通常包含四类题，各类的准备方式不同：

| 题型 | 占比（经验性） | 特征 | 准备方式 |
|---|---|---|---|
| 概念与原理 | 中 | "为什么 decode 是 memory-bound" | 理解机制，能推导 |
| **计算题** | 中 | "算这个配置的 KV cache" | **动笔练，直到不查公式** |
| **系统设计** | 高 | "设计一个 X 服务" | 用固定框架，反复演练 |
| **排查题** | 高 | "P99 高但均值正常，怎么查" | 建立症状→层的映射 |

> 占比为**本库基于公开岗位描述与常见考察范围的推论**，非统计数据。`待核实`

## 2. 原理、数学与性能模型

### 2.1 必须能动笔算的四类计算

这是本章最具操作性的部分。以下四类计算在推理面试中反复出现，且都无法靠背结论通过——面试官会改变参数。

**计算一：KV cache 容量**

$$
M_{KV} \approx 2 \times L \times B \times S \times H_{KV} \times D_h \times b
$$

**必须能做的变形**：固定显存反解并发上限；比较 MHA 与 GQA 的差异（改变 $H_{KV}$）；比较 FP16 与 INT8 KV（改变 $b$）；说明该式为何是近似。

**计算二：算术强度与瓶颈判定**

$$
I = \frac{\text{计算量 (FLOP)}}{\text{内存访问量 (byte)}}, \qquad
\text{Attainable} = \min(\text{Peak},\ I \times BW)
$$

**必须能做的**：说明为什么 decode 的 $I$ 远低于 prefill；由此推出 batch 增大对吞吐与时延的相反作用。

**计算三：排队与时延**

$$
L = \lambda W \qquad \text{(Little's Law)}
$$

其中 $L$ 为系统内平均请求数，$\lambda$ 为到达率（req/s），$W$ 为平均逗留时间（s）。

**必须能做的**：由目标并发与服务时间反推可承载的到达率；解释利用率接近 1 时排队时延为何急剧上升；说明这如何放大 tail latency。

**计算四：成本分解**

$$
\text{Cost per Token} = \frac{C_{accel} + C_{power} + C_{network} + C_{software} + C_{ops}}{\text{Delivered Tokens}}
$$

**必须能做的**：说明利用率如何进入分母；解释为什么硬件单价低不必然意味着服务成本低；指出哪些成本项常被忽略。

**共同要求**：每个公式都要能说出**假设、单位、以及它在什么情况下失效**。只会代入数字而说不出局限，在有经验的面试官面前会被识别为背诵。

## 3. 实现机制与系统设计

### 3.1 回答的固定结构

2–5 分钟的口头回答应当有骨架。推荐结构：

| 顺序 | 内容 | 时长 | 作用 |
|---:|---|---|---|
| 1 | **结论**（1–2 句） | 15 秒 | 让面试官立刻知道你的判断 |
| 2 | **核心原理** | 45 秒 | 证明结论不是猜的 |
| 3 | **设计/计算/排查路径** | 90 秒 | 展示可操作性 |
| 4 | **关键 trade-off** | 45 秒 | 展示成熟度 |
| 5 | **真实案例或论文** | 30 秒 | 展示阅读广度 |
| 6 | **局限或失败模式** | 30 秒 | **最能区分候选人的一段** |

**第 6 段为什么最重要**：绝大多数候选人在讲完方案后停下。主动说出"这个方案在 X 情况下会失效，因为 Y"，传达的是你真正部署过或深入思考过。

### 3.2 系统设计题的展开框架

直接复用 [04 系统设计方法论](04_how_to_design_an_inference_system.md) 的九步流程：

1. **先问清 workload 与 SLO**——不要直接开始设计。这一步本身就是得分点，因为它展示你知道设计需要输入；
2. 画出端到端骨架（[02 章](02_end_to_end_inference_lifecycle.md)的图）；
3. 算 KV 显存，反推硬件与并行策略；
4. 选调度策略并说明依据；
5. 主动提出可观测性与降级路径；
6. 最后说明你在哪里做了让步、为什么。

**时间分配**：45 分钟的设计题，前 5–8 分钟用于澄清需求是合理的，不是浪费。

### 3.3 排查题的展开框架

排查题的标准答法是**先分解再定位**：

1. 用六段分解确定劣化落在哪一段（排队/分词/prefill/decode/网络/后处理）；
2. 用 [02 章 3.2 节](02_end_to_end_inference_lifecycle.md)的层表列出候选层；
3. 说出每层要看的**具体指标**（队列深度、显存占用、抢占次数、集合通信耗时、频率曲线）；
4. 给出区分假设的实验（"如果是 A，我预期看到 X；如果是 B，会看到 Y"）；
5. 说明修复后如何验证。

**得分关键在第 3 和第 4 步**：能说出具体看什么指标、以及如何用观测区分竞争假设，比列出可能原因清单强得多。

## 4. 性能、成本、能耗与可靠性 trade-off

准备过程本身也有 trade-off：

| 取舍 | A 侧 | B 侧 | 建议 |
|---|---|---|---|
| 广度 vs 深度 | 覆盖所有模块 | 深入 3–4 个 | **深度优先**，广度靠 [模块 00](README.md) 兜底 |
| 论文 vs 实践 | 读更多论文 | 跑通开源引擎 | **至少跑通一个**，能讲实际观察到的现象 |
| 背题 vs 推导 | 记住答案 | 掌握推导 | **推导优先**，面试官会改参数 |
| 时间投入 | 突击两周 | 分散三个月 | 计算题需要**间隔重复**，突击效果差 |

## 5. benchmark、真实案例或公开部署案例

**建议的实践项目**（按投入产出比排序）：

| 项目 | 投入 | 你能在面试中讲什么 |
|---|---|---|
| 在单卡上跑通一个开源推理引擎并压测 | 低 | 实际的 TTFT/TPOT 曲线、batch 对二者的相反影响 |
| 测量并绘制吞吐-时延权衡曲线 | 低 | 亲眼见过的拐点位置与成因 |
| 对比不同量化配置的吞吐与质量 | 中 | 精度选择的实际代价 |
| 复现前缀缓存的命中收益 | 中 | cache 状态对 TTFT 的量级影响 |
| 用 profiler 定位一次性能问题 | 中 | 具体的排查过程与工具使用 |

**为什么这些比读论文更有价值**：面试官很难区分"读过 PagedAttention 论文"和"理解 KV 显存管理"，但很容易区分"我压测时看到并发到 X 之后吞吐反而下降，查下来是显存不足触发了抢占重算"这样的具体经历。

> 具体的可复现实验手册见 [模块 12](../12_open_source_deployment_and_reproduction/)（待撰写）。

## 7. 常见失败模式与排查路径

| 准备误区 | 表现 | 纠正 |
|---|---|---|
| 只记结论不会推导 | 面试官改参数后卡住 | 每个公式做 3 个变形练习 |
| 罗列技术名词 | 回答像特性清单 | 用第 3.1 节的六段结构 |
| 不问就开始设计 | 设计与实际需求不符 | 前 5 分钟专门澄清 workload 与 SLO |
| 讲方案不讲局限 | 显得没实际部署过 | 每个方案主动补一句失效条件 |
| 排查题只列可能原因 | 显示不出定位能力 | 说出具体指标与区分实验 |
| 引用无来源的数字 | 被追问来源时崩塌 | 只引用能说出来源的数字；否则说量级 |
| 假装知道 | 被追问后暴露 | **说不知道 + 说如何验证**，这是加分项 |
| 忽略成本维度 | 只谈性能 | 每个设计题主动带一句单位经济性 |

## 9. 小结

推理岗位面试考察的是约束下的工程权衡，而非技术名词覆盖面。四类计算——KV 显存、算术强度、排队时延、成本分解——必须能动笔做且能说出假设与局限。回答应遵循结论→原理→路径→权衡→案例→局限的六段结构，其中"局限"一段最能区分候选人。系统设计题复用九步方法论，排查题先做六段分解再映射到层。准备时深度优先于广度，推导优先于背诵，且至少跑通一个开源引擎以获得可讲述的实际观察。
